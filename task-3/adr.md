### <a name="_qmphm5d6rvi3"></a>**Решение**

![](/out/task-3/architecture/architecture.png)

Было принято решение решение использовать отдельный сервис оркестрации для управления всем процессом проведения платежей. Это позволит обеспечить разделение ответственности между командами и микросервисами во время разработки (NFR002). Так же, данный подход позволит легко подключать дополнительные проверки в процесс проведения платежа, такие как проверка прохождения комплаенс клиента и другие дополнительные проверки, которые могут потребоваться при изменении законодательных или юридических требований.

Взаимодействие со всеми сервисами проверок планируется реализовать с помощью асинхронного подхода, т.к. проверки могут требовать значительного времени для ответа. Например, они могут зависеть от внешних сервисов или ручных операций: сервис анти-фрод может отправить транзакцию на ручную проверку, которая может быть завершена в течении 20 минут.

В то время, как взаимодействие с платежным шлюзом должно происходить с помощью синхронного вызова для обеспечения атомарности операции и мгновенно подтверждения или отклонения операции от банка.

Данное решение позволяет легко масштабировать каждый из сервисов горизонтально, в том числе и сервис оркестрации для обеспечения необходимого уровня SLA (NFR001).

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

В качестве альтернативного решения можно рассмотреть реализацию логики оркестрации внутри сервиса платежного шлюза, превратив это в один большой **Платежный Сервис**. Но данное решение нарушает принцип единой ответственности сервиса и не позволит масштабировать только необходимые части из сервиса для поддержания требования по необходимому SLA. Так же стоит отметить, что при таком подходе становится сложным быстрое подключение дополнительных АПИ банков для выполнения банковских операций. Так же частые изменения в бизнес процессе проведения платежа (добавление новых сервисов проверок) потенциально может сломать взаимодействие с банковским АПИ.

**Недостатки, ограничения, риски**

- Недостатком выбранного решения является то, что необходимо разработать новый микросервис и полностью включить его в поддержку инфраструктуры (Наличие существующей DevOps команды и практики написания микросервисов, данный недостаток нивелируется)
- Платежный сервис является единой точкой отказа в проведении платежей по всей системе (нивелируется с помощью репликации и горизонтального масштабирования)
